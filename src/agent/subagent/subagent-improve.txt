我已经把雷1、雷3的实现现状和 `spawn_subagent` 的完整链路都抓出来了。先给结论：**两个雷的根因都确认了，且都有干净的"排队式"解法；同时发现工具描述之外还有一处真实的契约 bug，它比"描述写得不够好"更值得警惕。**

## 一、雷1：审批从「单例拒绝」改为「串行队列」

**现状锚点**：`desktop/main/ipc.ts:160-182`，关键在 161-163：

```ts
if (activeToolApprovalBatch) {
  reject(new Error('A tool approval batch is already pending in the sidebar.'));
  return;
}
```

这正是主/子并行时审批打架的直接来源：主 agent 的审批正在侧边栏 pending，subagent 后台再发审批，第二个直接被 reject，子 agent 那个工具调用报错、任务失败。这属于"用拒绝代替排队"。

**设计目标**：UI 仍然只展示一个 batch（侧边栏物理上就是单槽），但**不再拒绝，而是排队**，串行消费。

**方案**：在 `setupIpcHandlers` 内引入一个 pending 队列：

```ts
interface QueuedToolApproval {
  requests: readonly ToolApprovalRequest[];
  resolve: (decisions: readonly ToolApprovalDecision[]) => void;
  reject: (error: Error) => void;
}
const toolApprovalQueue: QueuedToolApproval[] = [];
```

改造 `setToolApprovalBatchHandler` 的逻辑：

1. 进来时，若 `activeToolApprovalBatch` 为空 → 正常创建 batch 并发布 UI 状态（现状逻辑保留）。
2. 若 `activeToolApprovalBatch` 非空 → `push` 到 `toolApprovalQueue`，**返回的 Promise 挂起，不 reject**。
3. 当当前 batch 的 `resolve` / `reject` 被调用（即 169-178 行现有回调）时，清空 `activeToolApprovalBatch` 后调用 `drainApprovalQueue()`：若队列非空，出队一个，promote 成新的 `activeToolApprovalBatch` 并发布 UI 状态。

**防饥饿的背压**：先实现最简单的 FIFO（可靠、无死锁）。若要防止某个 agent 海量 spawn 造成主 agent 审批被饿死，可加一层可配置上限——例如"每个排队来源最多 N 个 pending 位，超限才 reject"，这样"拒绝"从默认行为退化为最后的背压手段，而不是常态。

> 附带说明：`activeFileReview` 在 184-188 行是**同构的单例拒绝问题**，你没要求，但若要彻底消除并行打断，建议一并改成队列，结构完全复用。

## 二、雷3：并发上限从「拒绝式」改为「排队式」

**现状锚点**：`agent/subagent/subagent-service.ts:36-40`：

```ts
if (this.activeCount >= this.maxConcurrent) {
  throw new Error(`Max concurrent subagents (${this.maxConcurrent}) reached. Cannot spawn more.`);
}
```

第 6 个直接 throw，主 agent 若一口气 spawn 超过 5 个就静默失败。

**设计目标**：保留 `maxConcurrent = 5` 作为"同时在跑"的硬上限，但把"超出的"排队等待，而不是拒绝。

**方案**：

1. 扩展 `SubAgentStatus`（在 `subagent-types.ts`）增加 `'pending'` 状态。
2. `SubAgentService` 新增 `private readonly pending: Array<{ goal; options; resolve; reject }> = []`。
3. `spawn()` 逻辑改为：
   - 若 `activeCount < maxConcurrent` → 走现有路径，`status:'running'`，启动。
   - 否则 → 生成 `taskId`，把任务以 `status:'pending'` 先登记进 `agents` map（这样 `check_subagent` 能查到），再把启动闭包 push 到 `pending` 队列，**返回 taskId 而不 throw**。
4. 在 `onComplete` / `onError` / `cancel` 任何一处释放槽位后，调用 `drainQueue()`：从 `pending` 出队一个，把它的 `status` 改为 `running` 并真正 `agent.start()`。
5. 背压上限：新增 `maxPending`（如 10），超过才 throw——再次把"拒绝"降级为异常兜底。

**工具层配合**：`spawn_subagent` 的返回 summary 从 `"Sub-agent spawned with taskId"` 改为能区分 `"spawned (running)"` 与 `"queued (position N)"`，让 LLM 知道自己派的是"排队中"还是"已在跑"。

**与雷1的一致性收益**：排队后，尚未启动的 subagent 不会发出审批请求，天然降低了审批队列的压力——两个改动是协同的，不是各自为战。

## 四、关于「主 agent 很少调 subagent」的诊断

结论：**tool description 确实是主因之一，但根因是"只有工具描述、没有委派策略指令"——LLM 默认串行内联，不会主动并行化。**

证据链：

1. **描述只讲机制、不讲决策**。`agent/subagent/subagent-tool.ts:15-18` 全文：

```ts
'Create a new sub-agent that works on a given goal in the background. ' +
'Returns immediately with a taskId. Use check_subagent to poll for results.',
```

它只回答了"这个工具是干嘛的"（create/poll），**没有回答三个关键问题**：WHEN 该用、WHY 用了更快、不用时的代价是什么。`check_subagent`（48-49 行）同样只有一句。

2. **代码库里没有 system-prompt 级的委派指令**。我 grep 了 `delegate / 委派 / 并行 / sub-agent` 等，命中的全是 `tool-service.ts` 的注释、`loop-runner.ts` 的无关注释和设计文档——没有任何一处 prompt 文本告诉主 agent"遇到独立/可并行的子任务应优先 spawn"。也就是说，**工具描述是 LLM 唯一信号**。

3. **额外发现一个契约 bug（比描述问题更伤信任）**：工具描述和实现不一致。

   - 工具层 `subagent-tool.ts:70-83`：把 `{ budget, maxSteps }` **原样**传给 `service.spawn`。
   - 服务层 `subagent-service.ts:34`：签名却是 `{ maxSteps?, budgetLimit? }`。
   - 结果：LLM 按描述填了 `budget`，**被静默丢弃**，`budgetLimit` 走默认 25；同时 79 行 `budgetStrategy: options?.budgetLimit != null ? 'fixed' : 'fixed'` 是死代码（恒为 `'fixed'`）。

   这会让 LLM"设了预算却不生效"，进一步降低它对子 agent 能力的信任。

**改进建议（三层）**：

- **A. 重写描述，补上决策准则**（可直接替换 15-18 行）：

```
Spawn an independent sub-agent to run a self-contained goal in the background,
returning immediately with a taskId while you continue other work in parallel.
PREFER this when the task can be split into independent, long-running, or
parallelizable pieces (e.g. research N topics, write tests for separate modules,
read/analyze multiple unrelated files). AVOID when subtasks are strictly
sequential or need shared in-progress context. The sub-agent runs in its own
isolated context, so the goal must be self-contained (include all needed
context/constraints). After spawning, keep working and poll via check_subagent.
```

- **B. 在 system prompt 增加"委派策略"段落**：明确"独立/可并行/长耗时 → 派 subagent 后继续干；顺序依赖/强耦合上下文 → 内联自己做"。这是让 LLM 从"知道有工具"升级为"主动规划并行"的关键，单靠工具描述做不到。

- **C. 修契约**：统一 `budget` / `budgetLimit` 命名（建议工具层直接暴露 `budgetLimit`，或服务层接受 `budget` 别名），删掉 79 行死代码。

一句话总结：**描述不够好是表象，"缺少委派策略指令"是根因，"budget 参数被静默丢弃"是叠加的信任破坏**。三者一起修，主 agent 调用率会明显改善。
